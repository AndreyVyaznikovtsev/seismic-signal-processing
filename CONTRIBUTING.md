# Как участвовать

Проект работает по правилам обычного open source. Если вы делали вклад
в чужой проект на GitHub — здесь всё то же самое.

## Коротко

1. Найдите [issue](../../issues) и напишите в нём, что берёте задачу.
2. Создайте ветку от `main`.
3. Делайте небольшие осмысленные коммиты.
4. Откройте pull request.
5. Получите ревью, поправьте, дождитесь зелёного CI.

Прямой push в `main` запрещён. Всё идёт через pull request.

## Ветки

Имя ветки — от типа задачи и номера issue:

```
theory/12-convolution-support
example/15-aliasing-demo
lib/18-welch-psd
fix/21-circular-wrap
```

## Коммиты

Формат — `тег: Сообщение`, тег из фиксированного списка:

| Тег | Когда |
|---|---|
| `theory` | глава учебника, текст, формулы |
| `example` | практический разбор, ноутбук |
| `figure` | рисунок или его стиль |
| `lib` | код в `src/seisdsp/` |
| `tests` | тесты и проверки |
| `data` | работа с данными |
| `docs` | документы процесса, README |
| `ci` | сборка, хуки, автоматизация |

Сообщение начинается с заглавной буквы и с глагола:

```
lib: Добавить оценку спектра методом Уэлча
theory: Вывести пределы суммирования для свёртки
fix: Исправить заворачивание в circular_convolve
```

## Pull request

Заголовок — в том же формате: `тег: Название`.

Один pull request решает одну задачу. Если диф перевалил за четыре
сотни строк, почти наверняка стоило разделить: короткий PR разбирают
за день, длинный висит неделю и в итоге вливается непрочитанным.

Метки обязательны, по ним собирается changelog релиза.

**Чек-лист готовности** (Definition of Done) для главы или разбора:

- [ ] теория с выводом, а не пересказ результата
- [ ] исполняемый пример, вызывающий `seisdsp`, а не копию метода
- [ ] текст по [стилевому гайду](docs/style-prose.md)
- [ ] хотя бы один рисунок по [гайду](docs/figures-style.md)
- [ ] задача для читателя с решением под спойлером
- [ ] источники добавлены в `references.bib` и процитированы в тексте
- [ ] новая проверка в `src/seisdsp/verification.py`, если добавлен метод
- [ ] `make test` и `make lint` проходят локально
- [ ] CI зелёный

## Ревью

Каждый PR смотрят двое: владелец затронутого файла (см. `CODEOWNERS`)
и один назначенный рецензент.

Рецензия — это работа, и она оценивается наравне с самим вкладом.
Хорошая рецензия:

* проверяет, что утверждение в тексте следует из выкладки;
* ищет краевые случаи, которые код не покрывает;
* отличает замечание по существу от вкусовщины и помечает вкусовщину
  как необязательную (`nit:`);
* предлагает конкретную правку, а не «тут плохо».

Отвечать на замечания надо по каждому: либо правкой, либо аргументом.
Молча закрывать обсуждение нельзя.

## Код

* `ruff` со строкой в 90 символов, запускается хуком;
* русский текст — по [стилевому гайду](docs/style-prose.md);
* докстроки в стиле NumPy для всего публичного;
* функции не изменяют входные массивы;
* у каждого метода есть проверка в `verification.py`.

Поставьте хуки один раз:

```bash
pre-commit install
```

Тогда стиль чинится до коммита, и ревью не уходит в обсуждение пробелов.

## Данные

Файлы данных в git **не кладутся** — см. [data/README.md](data/README.md).
Хук `check-added-large-files` не пропустит файл больше 500 КБ.

## Использование ИИ

Пользоваться языковыми моделями можно — это рабочий инструмент.
Два требования:

1. Вы отвечаете за код, который принесли. «Так сгенерировалось» —
   не объяснение на ревью.
2. Если существенная часть PR сгенерирована, напишите об этом
   в описании. Это не штраф, это гигиена.

Проверяется не происхождение текста, а то, способны ли вы его
объяснить и поправить.
